Architecture Approaches

How to structure the routing and data layer for both customer pages and on-demand placeholder pages

A

Unified Route — /avis/[city]/[slug]

Single route handles all cases. Logic inside page.tsx decides: customer → full page, OSM/SIRENE listed → placeholder, unknown → URL-generated placeholder.

Customer lookup: Business.slug (existing) + optional Business.citySlug for city scoping
Non-customer: BusinessListing table, populated on-demand from OSM/SIRENE
Unknown: Generate display name from URL params, show CTA

Pros

  • One URL pattern for everything
  • Best SEO (city in URL)
  • Clean customer migration path

Cons

  • Adds city field to Business model
  • Existing /r/[slug] becomes legacy
B

Split Routes — /r/[slug] for customers, /avis/[city]/[slug] for discovery

Keep existing customer pages at /r/[slug] untouched. New /avis/[city]/[slug] route only handles non-customers (OSM/SIRENE or generated). Customer pages get a canonical link pointing to /avis/ for SEO.

Pros

  • Zero changes to existing customer pages
  • Clean separation of concerns
  • No schema migration risk

Cons

  • Two URL patterns for similar content
  • Customer avis pages lack city in URL
  • Duplicate content SEO risk
C

Unified Route with Redirect — /avis/[city]/[slug] is canonical for all

Same as A, but existing /r/[slug] redirects (301) to /avis/[city]/[slug]. Customers keep backward compat, new canonical URL is city-scoped. Customer must provide city when registering.

Pros

  • One canonical URL for all businesses
  • 301 redirect preserves SEO juice
  • City in URL for all pages

Cons

  • Requires city field in onboarding
  • Migration effort for existing customers
  • Redirect adds latency

My recommendation: C — Unified + redirect gives best SEO long-term. City in URL for every business. Old QR codes still work via 301. Small migration cost is worth it.
